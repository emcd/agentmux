## Why

Pty transport has two 0.9.0 blockers found live on 2026-08-20. A delivery to a Pty member panics in a tokio worker thread (`PtyPromptProbe::observe` at `src/pty/state.rs:122`/`128`, `blocking_send`/`blocking_recv` on a runtime thread) via `run_async_delivery_worker` (`src/relay/delivery/dispatch/worker.rs:144,177`) → `submit_batch:519` → `gate_target:927` → `is_ready_for_handover:837` → `PtyTransport::is_ready_for_handover` (`src/pty/transport.rs:972`) → `observe`, stranding the delivery forever while the relay stays apparently healthy (issues/runtime/8, corrected panic site). The gate runs on **every** batch submission to every Pty target, however the transport was constructed — a healthy eager worker is the case that reaches the probe, not the one that avoids it. Separately, Pty workers are *intentionally* lazy in `src/relay/lifecycle.rs:475` (`TargetConfiguration::Pty(_) => Ok(())` with a v1 stopgap comment), unlike Tmux (`startup_tmux_member` eagerly) and ACP (transport-contracts “ACP Persistent Worker Lifecycle” 523-536). That lazy construction leaves `issues/runtime/9` (held bundle still in catalog) reachable for Pty, but it is **not** the cause of the panic — the panic fix is group 1 alone, eager parity is a separate parity goal.

Why now: operator live reproduction with `--features pty` confirms the panic and the orphaned `opencode` child, and `todos/pty/9` 11.6/11.7 live validations are blocked on a Pty worker that actually starts.

## What Changes

- **Panic fix (blocking probe):** `PtyPromptProbe::observe` (`src/pty/state.rs:122`/`128`) and `PtyOutputView::look` (`src/pty/state.rs:75`) currently block a tokio worker thread via `blocking_send`/`blocking_recv` through the worker’s `mpsc`/`oneshot` channel. The probe is reached on **every** Pty delivery via `worker.rs:837` (`gate_target` → `is_ready_for_handover`), not just the lazy path. Fix by making the handshake non-blocking (`async send`/`await` or `try_*` + `await`) in `src/pty/state.rs` — `submit_batch` (`worker.rs:900`) holds `&mut TransportImpl` plus `&mut` borrows of the window/activity/inflight maps, so lifting the read into `spawn_blocking` at the caller would require restructuring the gate and is more expensive than an async handshake in `state.rs`. `build_worker_transport` already runs `startup` off-runtime via `start_transport_off_runtime` (`envelope.rs:93-110`) and already propagates its error (`envelope.rs:215-220` “Propagated rather than discarded”) — there is no `let _ =` to fix.

- **Eager-startup parity — deferred:** Bringing Pty to the same lifecycle parity Tmux and ACP already have (`ACP Persistent Worker Lifecycle` 523-536) requires a `WorkerTransportSource::Pty` handoff analogous to `Acp(AcpWorkerBootstrap)` (`worker.rs:81-86`); Pty is currently `Direct` where the delivery worker builds its own `TransportImpl` (`worker.rs:184-190`), so constructing in `lifecycle.rs` without a handoff double-spawns. This group is **deferred to a follow-up change** that scopes the handoff. The `Pty Persistent Worker Lifecycle` requirement is **not landed in this change’s delta**; `lifecycle.rs:475` stays `Ok(())` for this change.

- **Held-bundle guard (issues/runtime/9) — must land with group 1:** Add a single `BundleCatalog::is_held` check at delivery-group construction (`src/relay/handlers/send.rs:883` `ensure_bundle_group` and `src/relay/handlers/routed.rs:85` `resolve_target_bundle` via `catalog.rs:162`/`watcher.rs:308`) before any `build_worker_transport` call; if held, reject as `unavailable` (per `issues/runtime/9` preference for reject, spec delta asserts it). Group 1 unmasks this hole (today a `send` to a held Pty bundle spawns then panics; after the probe fix it would spawn and succeed — a silent hold violation), so the guard is load-bearing for this change and not deferred with eager parity. Encode once so every future transport inherits it.

- Specs: `transport-contracts/spec.md` — ADDED `Pty Prompt Probe and Look Shall Not Block a Tokio Worker Thread` (group 1, the blocker) and ADDED `Held Bundle Deliveries Shall Not Spawn Workers` (group 3, must land with group 1 — otherwise group 1 unmasks `runtime/9` from loud panic to silent hold violation). `Pty Persistent Worker Lifecycle` (eager startup) is **not** in this delta; deferred to follow-up with the `WorkerTransportSource::Pty` handoff.
- Tests: un-ignore `tests/integration/cli/pty_state_propagation.rs` two `#[ignore]`d rendezvous tests once the probe panic is fixed — they pass unchanged after group 1 alone (group 1 *is* the whole blocker fix); no eager test in this change. - Dependencies: requires `cargo build --features pty` (needs Zig 0.15.x) for Pty code to be compiled; `default` build still has no Pty transport (feature-gated `SessionType::Pty` arm).
